# PHY6252 model

PHY6252 is the first executable SoC in Firmverse. It is also the regression target that protects the platform refactor from becoming a directory-only abstraction exercise.

## Execution

- CPU backend: vendored `jjkt/zmu`.
- CPU profile: Cortex-M0 / ARMv6-M.
- Firmware format: Intel HEX.
- Default board: `pb03f-kit`.
- Alternative board: `headless`.

```sh
firmverse --strict --once firmware.hex
```

Strict mode stops on firmware-visible behavior that has not been modeled instead of converting unknown MMIO/ROM accesses into successful no-ops.

## Implemented surface

The current strict regression exercises:

- relocated Cortex-M0 vectors and SRAM;
- 256 KiB XIP/NOR behavior;
- GPIO;
- UART0/UART1;
- SCB `AIRCR.SYSRESETREQ` as a PHY6252 software/system reset source;
- PHY6252 ROM UART0 programmer entry (`9600`, `UXTDWU`, `cmd>>:`, command mode at `115200`);
- four ADC channels used by the board/demo firmware;
- six PWM channels;
- timers;
- PCR/AON/cache/clock behavior reached by firmware;
- SPI-flash/NOR erase and program semantics;
- optional persistent NOR state;
- DMAC paths used by capability firmware;
- eFuse/AES bootstrap behavior;
- ARM EABI helpers;
- OSAL memory, queues, events, timers and task dispatch;
- exercised PHY6252 HCI/LL/GAP/GATT/security ROM ABI;
- generic ATT RX/TX mailbox transport;
- strict discovery of missing MMIO/vendor-ROM behavior.

This is an executable model of the surfaces exercised by known firmware, not a claim of transistor-, RF- or cycle-accurate PHY6252 simulation.

## ROM UART programmer

Firmverse models the development path used by the PHY6252 ROM programmer rather than faking a board-level RTS/DTR reset line.

When guest firmware executes the CMSIS `NVIC_SystemReset()` path, the Cortex writes `SCB.AIRCR` with `VECTKEY` and `SYSRESETREQ`. Firmverse intercepts that architectural write at the SoC boundary and puts the virtual PHY6252 into its ROM UART0 entry window:

```text
UART ROM0@9600 await UXTDWU
```

Drive the ROM entry exactly as a flashing harness would:

```text
UART 0 9600 UXTDWU
```

The virtual ROM responds:

```text
UART ROM0@9600 cmd>>:
```

and moves to the 115200-baud command-monitor state. The currently modeled monitor command is the reset path used to return to the application:

```text
UART 0 115200 reset
```

This surface is intentionally narrow. It proves and regression-tests the important control transition

```text
application -> SYSRESETREQ -> ROM -> UXTDWU -> cmd>>: -> application
```

without inventing undocumented ROM internals. Full `rdreg`/erase/program/cpbin command emulation can be layered onto the same state machine when a harness needs to run the vendor/pvvx programmer end-to-end.

## Package pins

Package pad mapping belongs to the SoC and is defined in `src/soc/phy6252/pins.rs`.

| Pad | AP_GPIO bit | ADC channel |
|---|---:|---:|
| P0 | 0 | — |
| P2 | 2 | — |
| P3 | 3 | — |
| P7 | 4 | — |
| P11 | 7 | — |
| P14 | 8 | — |
| P15 | 9 | 1 |
| P16 | 10 | — |
| P17 | 11 | — |
| P18 | 12 | — |
| P20 | 13 | 0 |
| P23 | 14 | 3 |
| P24 | 15 | 2 |
| P31 | 19 | — |
| P32 | 20 | — |
| P33 | 21 | — |
| P34 | 22 | — |

Board-specific meaning is deliberately absent from this table.

For example:

- `P7 -> AP_GPIO bit 4` is PHY6252/package metadata;
- `P7 -> red LED` is PB-03F board metadata;
- `P15 -> ADC1 / AP_GPIO bit 9` is PHY6252/package metadata;
- `P15 -> Restore` is PB-03F board metadata.

The TUI consumes both layers instead of maintaining a third copy.

## PB-03F-Kit

`BoardProfile::Pb03fKit` owns:

- the physical DIP-30 connector rows;
- LED colour-to-pin meanings;
- Restore meaning;
- connector notes such as UART0 TX/RX, power and NC labels.

Indicator mapping:

| Function | Pin |
|---|---|
| red | P7 |
| green | P11 |
| blue | P18 |
| yellow | P0 |
| white | P34 |
| Restore | P15 |

`headless` keeps PHY6252 execution but intentionally has no PB-03F connector or LED semantics.

## Persistent NOR

Set `PHY6252_FLASH_STATE` to preserve the full NOR image between runs:

```sh
PHY6252_FLASH_STATE=.state/device.flash \
  firmverse --strict firmware.hex
```

The persisted state is checked against the baseline firmware image before restoration.

## Regression firmware

Build freestanding demo/regression images:

```sh
make -C firmware clean all
```

Important images:

- `kit-demo.hex` — board interaction smoke;
- `rssi-rank.hex` — advertiser ranking and PB-03F indicator behavior;
- `capability-demo.hex` — strict regression across OSAL, flash, AES, controller ABI, GPIO/ADC/PWM/UART and DMA.

CI also builds a real vendor PHY62XX SDK 3.1.2 BLE image and validates its provenance before the emulator regressions run.

## Real hardware

The real-device flashing path is SoC-specific and intentionally separate from the virtual hardware ownership model.

```sh
cargo run --release --bin phy6252-flash -- firmware.hex
```

See [`../HARDWARE_FLASH.md`](../HARDWARE_FLASH.md) for ROM bootloader/CH340/SDK details.
