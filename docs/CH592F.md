# CH592F direction

The WeAct Studio CH592F Core Board is registered in Firmverse, but it is intentionally not executable yet.

## Why it is a separate SoC

CH592F is not a PHY6252 board variant. Its execution path requires a different CPU/backend boundary and a different memory/MMIO model.

Firmverse currently records:

- SoC ID: `ch592f`;
- board ID: `weact-ch592f`;
- CPU/backend intent: `riscv/qingke-v4c`;
- execution state: not implemented.

Selecting `weact-ch592f` therefore fails closed instead of silently running the image against PHY6252 behavior.

## Implementation order

The first CH592F milestone should be deliberately small:

1. firmware image loader;
2. reset/entry state;
3. memory map;
4. CPU execution backend for the required QingKe/RISC-V instruction/interrupt behavior;
5. fail-closed MMIO bus;
6. enough clock/GPIO/UART behavior to execute a minimal real firmware image;
7. only then populate the WeAct board wiring profile.

BLE/controller emulation should follow executable boot/basic-peripheral coverage rather than being invented ahead of observed firmware requirements.

## Target source shape

```text
src/soc/
  phy6252/
  ch592f/
    mod.rs
    loader.rs
    memory.rs
    cpu.rs
    bus.rs
    gpio.rs
    uart.rs
```

The exact module split can evolve, but CH592F code must not enter `soc/phy6252/` and board wiring must not enter the CH592F SoC implementation.

## Hardware-assisted validation

Once the basic backend exists, the preferred validation path is differential:

- run a small test firmware in Firmverse;
- run the same firmware on the physical WeAct CH592F board;
- capture observable UART/GPIO/timing traces;
- compare the traces and close model gaps explicitly.

That keeps the second SoC from accumulating unverified compatibility shims copied from the first one.
